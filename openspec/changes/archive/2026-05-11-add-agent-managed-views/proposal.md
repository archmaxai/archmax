# Change: Agent-managed DuckDB views with persistent storage

## Why

Today the per-model scoped DuckDB views (`_scope_<modelName>."<dataset>"`) are auto-derived from each dataset's `fields` array — every view is mechanically a `SELECT <field expressions> FROM <source>` mirror of the source table (`packages/core/src/services/duckdb.ts:473-526`). Two consequences follow:

1. **The agent has no leverage over the view body.** It cannot project a subset of rows (no `WHERE`), denormalize via joins, exclude noisy partitions, or otherwise shape what AI consumers see. Anything beyond a column-projection mirror requires changing TypeScript code, not the model.
2. **The agent cannot test what it just wrote.** The DuckDB instance lives in memory (`DuckDBInstance.create()` with no path), so views vanish on every API restart and there is no persistent artefact the agent can poke at to confirm its model actually resolves. The agent has to *hypothesise* that the join graph and field expressions it just authored will resolve in DuckDB, which is the single largest source of model-correctness bugs.

We want the agent to author each dataset's view body explicitly (as a `view_query` custom extension), persist the DuckDB database to the project's data directory so views survive across processes, and let the agent prove correctness by running the same query the MCP server will run.

## What Changes

- Add a `view_query` field to the `COMMON` `custom_extensions` payload on every dataset. It is a single `SELECT … FROM <connection>.<schema>.<table> …` statement that defines the dataset's scoped view body. `view_query` MAY include `WHERE`, `JOIN`, computed projections, and any expression DuckDB accepts in a SELECT. It MUST resolve to columns whose names match the dataset's declared field `name`s.
- Replace the auto-derivation logic in `createScopedViews` with a stateless `materialiseModelViews(projectId, model)` helper that, on every call, runs `CREATE OR REPLACE VIEW _scope_<modelName>."<dataset>" AS <view_query>` for every dataset with a non-empty `view_query`. There is no in-memory hash cache; idempotency comes from `CREATE OR REPLACE`. The single source of truth is the dataset's `view_query` in YAML; the persistent DuckDB file is the materialised reflection.
- **Split the agent's SQL surface into two tools.** `executeQuery` stays as the agent's catalog-exploration tool (fully qualified `catalog.schema.table` references — `information_schema`, sampling raw source tables, validating join cardinalities). A new `runModelQuery({ modelName, sql, params })` tool is the agent's view-testing surface: it shares `materialiseModelViews` with the MCP path, runs against the model's scoped views, and is the canonical way for the agent to verify a `view_query` it just wrote produces the right rows.
- Make the project-level DuckDB instance file-backed at `<ARCHMAX_DATA_DIR>/projects/<projectId>/duckdb.db`. The file is opened read-write (so views can be created), attached source catalogs remain `READ_ONLY`, and `enable_external_access` stays disabled outside of iceberg cases. The file persists across process restarts. DuckDB iceberg secrets are forced to `TEMPORARY` so bearer tokens never reach disk. The persistent file is gitignored. Operational hygiene (graceful shutdown lock release, `?reset=true` flag on the existing reinit endpoint, recoverability when the file is deleted out-of-band) is folded into the existing `DuckDB Federation` and `Connections Reinit Endpoint` requirements rather than getting separate top-level requirements.
- **Hide `_scope_<modelName>` from agent-visible surfaces.** Tool descriptions, the system prompt, and tool-result error messages all use bare dataset names; any DuckDB error mentioning `_scope_<modelName>.` has the qualifier stripped before being returned to the agent. The structural SQL validator from `add-structural-sql-safety` enforces that quoting variants of `_scope_*` (plain double-quote, unicode-escaped, dollar-quoted) cannot bypass the lexical regex — this is the security boundary that keeps every model's views in their own sandbox.
- Ship a one-time migration (`apps/api/src/scripts/migrate-view-query.ts`) that backfills `view_query` for every existing dataset by emitting the SELECT body that `createScopedViews` would have generated. After migration, every dataset has an explicit `view_query` and the auto-derivation code path is removed. **BREAKING** for any caller that constructed a model in memory without running through the file service / migration. Datasets with an empty `fields` array are NOT silently skipped: they emit a WARN log and count under "errored" so a CI run of the script exits non-zero, surfacing them for operator attention.
- Update the semantic-model-agent prompt: tools section gains `runModelQuery`, workflow steps gain "4f Author the dataset's view_query" and "4g Test the view via runModelQuery", "Field Names vs Physical Columns" stops describing the auto-derived `SELECT … FROM <source>` shape, the COMMON Extension Fields reference and Important Rules add `view_query`, and every reference to `_scope_*` is removed from agent-facing copy.

## Impact

- Affected specs:
  - `semantic-models` — new requirement for `view_query` custom extension + migration script (with loud failure for no-fields datasets).
  - `mcp-server` — `Scoped DuckDB VIEWs` requirement modified to read from `view_query` and to use `CREATE OR REPLACE` on every call (no cache); `MCP Query SQL Validation` requirement modified to mandate that the structural validator rejects every quoting variant of `_scope_*` schemas.
  - `data-connections` — `DuckDB Federation` requirement modified for file-backed instance, ephemeral iceberg secrets, gitignore, and graceful shutdown; `Project DuckDB Instance Disposal` modified for file-lock release; `Connections Reinit Endpoint` modified to add the `?reset=true` flag.
  - `semantic-model-agent` — `executeQuery Tool` requirement modified to scope it to catalog exploration only; new `runModelQuery Tool` requirement; new `Agent Surfaces Hide Scoped Schema Name` requirement.
- Affected code:
  - `packages/core/src/services/duckdb.ts` — `getProjectInstance` opens a file path; `createScopedViews` is replaced by stateless `materialiseModelViews`; `disposeProjectInstance` closes the file lock; iceberg secrets become `TEMPORARY`. `scopeViewCache`/`computeModelHash`/`invalidateScopedViews` are removed.
  - `packages/core/src/services/semantic-model-schema.ts` (or sibling) — Zod parser for the `view_query` field inside the COMMON extension.
  - `packages/core/src/services/mcp-tools.ts` — `executeScopedQuery` calls `materialiseModelViews`; missing `view_query` returns documented error.
  - `packages/core/src/services/agent-tools.ts` — `makeExecuteQueryTool` description tightened to "catalog exploration only"; new `makeRunModelQueryTool` shares the materialisation helper; `buildConnectionContext` gains a single-sentence reminder; every `_scope_` mention removed from agent-visible strings.
  - `packages/core/prompts/semantic-model-agent.md` — multi-touchpoint update: tools section (add `runModelQuery`), workflow steps 4f/4g (author + test view), Field Names vs Physical Columns paragraph, YAML Conventions and COMMON Extension Fields reference (add `view_query`), Important Rules (forbid auto-derivation), Complete Example (add `view_query` to each dataset). All `_scope_*` references removed.
  - new `apps/api/src/scripts/migrate-view-query.ts` and matching test.
  - tests across `packages/core/src/services/duckdb.test.ts`, `mcp-tools.test.ts`, `agent-tools.test.ts`, agent integration tests, and `apps/e2e`.
  - `apps/docs` — guides for "Authoring views" and reference for the COMMON extension.
- Cross-change dependency: this change extends the `add-structural-sql-safety` change's validator to add `_scope_*` to its forbidden-schema list and adds parser-evasion test corpus for quoted/unicode-escaped variants. If `add-structural-sql-safety` does not land first, this change's `_scope_*` quoting-evasion scenarios fall back to lexical-only protection (still safe; just less defence in depth).
